# 调研与深入分析

本流程适用于 A 屏幕拆解、B 找参考、C 功能调研。先确定问题和深度，再选择工具。

## 1. 定义要回答的问题

记录产品/平台、用户要作出的决定、已有约束和目标深度。用户已提供的事实不重复询问。
普通调研默认 L2；“怎么实现的”以 L3 为目标；明确要我方落地时增加 L4/L5。

| 深度 | 要回答的问题 | 必要交付 |
|---|---|---|
| L1 功能表现 | 有什么入口、能力、限制？ | 带证据的功能清单 |
| L2 行为机制 | 如何触发、变化和恢复？ | 主流程、状态与一条边界/失败路径 |
| L3 实现链路 | 操作到结果经过哪些处理？ | 操作→处理→数据交互→状态更新，每个关键节点有定位 |
| L4 设计取舍 | 哪些解释符合证据，有什么替代方案？ | 假设、区分观察、替代方案与代价；动机标推断 |
| L5 我方落地 | 我们如何做同类能力？ | 模块、接口、状态模型、约束、验证方案，标为我方建议 |

深度是目标，不是保证。分别记录 target_depth、achieved_depth、gaps；不能用篇幅或推断填满未知节点。
可以在 L3 未完整时提供我方设计建议，但不得称已还原对方的完整实现；achieved_depth 应保持在已有证据支持的层级。

将大问题拆成可观察命题，例如自动分章节：触发方式、输入限制、等待/部分结果、编辑、失败恢复、导出联动。
每个关键问题都必须有结论或 SKIP 和原因；有源码且可合法使用时直接读源码。

## 2. 选择目标与来源

A 使用指定目标。B 默认三条发行参考，尽量混合 Web/App。C 选择两到三个功能相关、可访问且能取得证据的目标；用户指定数量优先。
为每个候选写一句纳入/排除理由，比较功能相关性、版本/平台和可达性，不按知名度排名。

按具体问题搜集官方帮助/发布说明、公开演示、实际操作、包内/公开脚本线索和用户报告。
搜索词包含功能名、动作、失败文案、同义词；记录 URL/文件定位、发布时间（未知则注明）、访问时间和账号/套餐/地区/版本条件。
官方说法只证明官方作过该声明；用户报告只证明有人这样陈述。多个转述同一来源不能算独立证据。

## 3. 先提出解释，再设计观察

对关键机制维护一张小表：

| 待解释现象 | 候选解释 | 能区分它们的观察 | 已有证据/缺口 |
|---|---|---|---|
| 搜索第二次很快 | 网络缓存、应用缓存、预取、本地计算 | 比较首次/重复操作、已可见的缓存标记与请求；不默认清缓存改变环境 | 未验证的解释保持并列 |
| 旧搜索结果没有覆盖新结果 | 取消旧请求、序号检查、响应顺序碰巧一致 | 查看取消事件/可读代码；乱序验证只在自制样本做 | 一次正常结果不能证实机制 |

采用能区分解释的最少观察。一次无请求不证明缓存，一次延迟不证明防抖，飞行模式失败不证明云端算法。
重复、断网、限速、改响应等都会改变条件；将实验记录与正常行为分开。公网目标不主动枚举/重放发现的接口。
产生数据、消耗配额等沿用已约定边界；尚未授权的操作先问，其他只读工作继续。

## 4. 沿一条具体链路深入

Web：目标元素/状态 → 事件或公开脚本处理 → 参数构造 → 请求/响应 → UI 更新。
Android：界面 → Manifest/资源 → 类/方法 → 原生/JS 桥接或请求 → 界面结果。

为节点保存来源文件/URL、采集时间、哈希或版本和行/方法/事件定位。箭头也需要依据；时间接近只支持候选关联。
Web 仅查看公开加载且可访问的脚本/source map，不猜隐藏路径，不跨访问限制。代码不可读时交付可观测部分。
第三方 SDK、后台埋点、同名字符串不可直接归属于目标功能。跨到服务端、混淆或缺失模块时注明断点。

## 5. 处理冲突并形成建议

将冲突证据并排比较，先核对是否版本、地区、套餐、账号、平台或采集条件不同；解释不了保留 unresolved。
报告分开写：

- 观察：这次请求被取消（事件定位）。
- 推断：这可能是为避免旧响应覆盖新输入；其他解释仍存在。
- 我方建议：采用请求序号校验，并在适用时取消旧请求；用乱序响应样本验证。

停止条件：关键问题均有答案或明确缺口；新增观察不改变建议；或已到用户约定的账号/配额/操作边界。
深入报告至少检查：一条可追溯链路、一个机制的替代解释、一条异常/边界路径、未知边界，以及适用时的我方实现和测试建议。
不能达到时降低 achieved_depth 并解释，不伪造满足条件。

## 6. 报告模板与验收

1. 用户要作出的决定、约束、目标/实际深度。
2. 结论与参考对象比较：哪些已观察，哪些是声明或推断。
3. 功能卡：入口/前置、输入/校验、触发、状态、限制、并发/恢复、联动。
4. 实现链路与假设表：证据、反证、替代解释、未知断点。
5. 我方方案：采用/不采用什么、实现条件、状态与接口、验收办法。
6. 证据索引、覆盖表、PASS/PLAUSIBLE/SKIP 与剩余问题。

结构化记录见 [evidence-format.md](evidence-format.md)。执行：

```sh
python3 scripts/check_report.py examples/research/report.json
python3 scripts/test_regressions.py
```

VALID 只代表字段和已声明边界合法，不证明事实真实、来源可靠、实际深度达到或所有敏感信息已移除。
