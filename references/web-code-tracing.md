# Web 定向代码阅读（L3）

这是一份取证流程，不是已实现的自动反编译器。先读 research-workflow.md；只有与问题有关时才往下追。

## 输入与定位

从用户动作和目标元素出发，结合已取得的请求/状态记录提出一个具体问题：
“搜索参数在哪里构造”“旧请求结果如何丢弃”“加载态何时结束”。

只阅读浏览器已公开加载、任务允许访问的脚本。source map 仅在实际声明且可合法读取时使用；
不猜隐藏路径，不绕访问限制，不把一个产品的开源库实现等同于该产品当前上线代码。
记录脚本 URL、获取时间、内容 SHA-256、部署版本（未知则写 unknown）和映射文件来源。
URL 参数可能带访问凭据，公开报告应脱敏；原始代码与 map 放仓库外。

## 最短完整链路

1. 入口：事件/组件与实际用户操作的关联依据。
2. 处理：输入校验、状态判断、参数构造；区分调用点与库的能力。
3. 数据：请求、响应字段或本地处理的可读代码及运行观察。
4. 更新：响应如何进入状态/DOM，失败和并发如何处理。

每个节点与箭头注明证据。保存原始脚本定位；有 map 时同时保存映射位置，不能只留下失去版本信息的行号。
混淆、动态加载、反射/框架调度、代码分割、缺 map 或进入服务端后可以使链路中断；写出已看到的部分与未知边界。
响应里一个字段名不能证明服务器算法或数据库结构；SDK 的存在不能证明目标功能调用了它。

## 区分事实、解释与我方方案

- 静态事实：此版本的这个处理函数有取消调用，或序号比较分支。
- 运行观察：本次操作确有取消事件，或旧响应没有更新界面。
- 机制推断：二者是否指向同一链路，有什么替代解释？
- 我方方案：可以采用相同模式，但按我方平台/状态约束设计并验证。

静态与运行证据都在也不自动构成因果证明。若仅能证实局部链路，不宣称整体 L3 已完成。
L4 比较替代方案的代价；L5 明确我方接口、状态模型及测试，不能编造对方的设计动机。

## 验收

报告应有一条有定位的链路、至少一个替代解释或已排除理由、一条异常/边界路径、明确未知范围。
真值样本中加入同名文案的无关组件，检查是否错误归属；在自制样本模拟乱序/取消，不在真实产品上改写响应。
若关键证据拿不到，记录 target_depth=L3、achieved_depth=L1/L2 和具体 gaps，交付现有发现。
