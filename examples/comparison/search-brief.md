# 示例 B：内容搜索该选哪种机制？

这是自拟设计问题，不代表用户已经选择产品方向。约束假设：先做中文知识库搜索，桌面和手机均使用，暂不要求离线。资料核对日期 2026-10-08；App 没有真机实测。

| 发行参考 | 一句话机制 | 证据与缺口 | 适配条件 |
|---|---|---|---|
| Wikipedia 首页（Web） | 输入后给文章候选，点选后进入文章 | 本次 Chromium 观察了建议出现和清空；脚本/请求支持客户端局部链路，服务端未知 | 文档标题清晰、目标是快速进入内容 |
| Firefox for Android（App） | 同一输入框汇合标签页、书签、历史与搜索引擎建议 | [官方帮助](https://support.mozilla.org/en-US/kb/searching-firefox-android)（页面标更新 2024-04-01）声明这些来源；本次未操作 App，地区/设置会影响结果 | 本地收藏和已访问内容与新内容同样重要 |
| Kiwix JS PWA（Web） | 在已下载的 ZIM 内容中检索，全文能力依赖版本与索引 | [产品内帮助](https://pwa.kiwix.org/www/index.html)说明离线文件前提及全文/标题搜索；未下载 ZIM，未实测检索 | 必须离线，能够接受包体、存储及更新成本 |

三者都让输入靠近结果入口，但数据来源、更新方式与隐私条件不同。Wikipedia 适合作为标题候选方向；Firefox 展示多来源汇合；Kiwix 展示离线内容约束。后两项是来源陈述，不是运行 PASS。

在上述假设下，建议先选标题候选路径，之后再考虑历史/收藏；这是设计建议，不是性能测试结论。若离线是硬约束，推荐会改为优先验证本地索引与内容包方案。

下一步应让需求方在“快速进入文档 / 汇合个人历史 / 离线检索”中选择，再对选定方向拆屏和量化。不要直接复制 Wikipedia 的 JSONP 传输方式，也不要从产品文档推断服务端内部架构。

| 结论 | 结果 |
|---|---|
| Wikipedia 本次输入后出现建议 | PASS（浏览器观察，详见 Web 案例） |
| Firefox/Kiwix 官方资料包含以上说明 | PASS（仅资料内容） |
| 当前 App/离线搜索在此环境可用 | SKIP |
| 标题候选适合假设中的首版知识库 | PLAUSIBLE（我方建议） |
